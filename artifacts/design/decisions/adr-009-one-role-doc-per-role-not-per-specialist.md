# ADR-009: One role doc per role; specialization lives in spawn brief

**D-ID:** D-004 (parent strategic decision)
**Status:** Accepted
**Date:** 2026-04-28
**Context:** Architecture design for wide-team specialization (Surface 8 of `artifacts/planning/brainstorm-wide-team-2026-04-28.md`)

## Context

The brainstorm posed a generator question: when a fixed-mode project declares N specialist developers (e.g., `backend-auth`, `backend-upload`, `frontend-dashboard`), should the generator emit N separate role documents (`developer-backend-auth.md`, `developer-backend-upload.md`, ...) — each pre-customized with the domain — or should there continue to be exactly one `developer.md` and have the orchestrator inject the domain via the spawn brief?

The brainstorm proposed the second option as the default but asked the architect to confirm or override with rationale.

## Decision

There is exactly **one `developer.md`** (and one `reviewer.md`). Specialization for fixed-mode wide-team specialists is conveyed via the spawn brief generated by the orchestrator at TeamCreate time. The brief includes:

1. The domain name (from `swarm.yaml:team.specializations[i].domain`).
2. The free-text description (from `team.specializations[i].description`).
3. The relevant slice of the architecture's domain map for that domain.
4. The story file (whose `## Domain:` matches).

The role doc itself is not modified per specialist. No `developer-backend-auth.md` file exists. No new generator runs over `team.specializations` to emit per-domain role docs.

## Alternatives considered

- **A. Per-specialist role docs emitted by a new generator.** This is the option the brainstorm asked the architect to evaluate. Concretely, `agent-generator.js` (or a new sibling) would walk `team.specializations` and emit `.claude/agents/developer-<domain>.md` files, each with the domain pre-injected into the front matter or template. Rejected for these reasons:

  1. **No behavioral difference.** A specialist developer behaves identically to a generic developer: same TDD cycle, same halt-on-blocker, same story-as-authority rule. The role's behaviors are constant; only the *task instance* changes (which domain, which stories). Encoding task-instance into a per-specialist file confuses two layers — same critique as the existing per-lens decision (lenses are passed via spawn args, not via per-lens role docs).

  2. **Generator complexity multiplies for no payoff.** N specialists × M roles = N×M generated files. Each must be tracked for the `_bmadGenerated` hash, the manual-modification detection, the eject mechanism. The eject decision tree alone (eject `developer.md`, or eject `developer-backend-auth.md`?) is a new question with no clean answer.

  3. **Per-specialist files create a sync problem.** Domain rename in `swarm.yaml` would need to delete the old file and emit the new. Domain removal would need to delete the file. Mid-epic injection (architecture.md §6.3) would need to emit a new file at runtime. Each of these is a new generator-side state-management problem.

  4. **The role doc is a contract with the agent, not a template for its task.** Looking at `agents/developer.md` today: it describes what a developer DOES, not what it KNOWS about a specific project. Domain knowledge is project state, which `swarm.yaml` and the architecture document already carry. Duplicating it into a role doc is a copy that must be kept in sync with the source.

- **B. Per-specialist files only when the user requests deep customization** (e.g., `team.specializations[i].extra_rules: [...]`). Rejected for v1: introduces a forking pattern (one specialist gets a custom file, the rest don't) and prematurely solves a problem nobody has reported. The existing per-agent `extra_rules` and `extra_context` mechanism (`generators/agent-generator.js:78-88`) already handles role-wide customization. Per-specialist customization, if ever needed, is a follow-up.

- **C. Inject specialization via YAML frontmatter on the role doc.** Considered seriously. Rejected because there is one role doc serving N specialists — frontmatter is a single value, can't carry N domain assignments. Would force option A.

- **D. A `specializations.md` companion file referenced from `developer.md`.** Rejected: equivalent to A but with worse ergonomics (one more file to find, one more layer to indirect through).

## Consequences

**Positive**

- Generator complexity stays at zero. `agent-generator.js` continues to walk `agents/*.md` exactly as today; no new file enumeration, no new emission rules.
- The eject mechanism is unchanged. Ejecting `developer.md` affects every specialist (and the fallback) — predictably, and consistent with how it works for the lens-as-spawn-args pattern today.
- Domain rename / removal in `swarm.yaml` is a config-only change. No file regeneration required.
- The role doc's source-of-truth property holds: it describes role behavior, full stop. Project state stays in `swarm.yaml` and `artifacts/`.
- Mid-epic injection (architecture.md §6.3) is trivial: orchestrator just spawns with a different domain in the brief. No file emission at runtime.

**Negative**

- A specialist that needs genuinely role-altering behavior (e.g., a security-focused dev with a different test-coverage rule) cannot get it without ejecting `developer.md` (which affects all specialists). Mitigated: this case is handled by the existing per-agent `extra_rules` mechanism if it's role-wide; truly per-specialist behavior is a deferred problem (not in scope for v1).

- The spawn brief grows. The orchestrator must compose the brief carefully, embedding the right slice of architecture and the right description. This is real work, but it's already what the orchestrator does today for lens-bearing reviewers and for context-curated TeamCreate calls.

**Forward-compatibility**

- If per-specialist role docs are ever genuinely needed, ADR-009 can be revisited and a new generator added. The current design does not preclude that future. It just declines to do it now in the absence of a forcing function.

## Verification

1. The `agent-generator.js` source contains no reference to `team.specializations`. The generator's behavior for `developer.md` is unchanged before/after this feature lands.
2. Spawning a specialist via TeamCreate produces a teammate that loads `developer.md` (via `/identity-developer`) — same identity-loading flow as a generic dev today.
3. The orchestrator's spawn brief, when inspected for a specialist TeamCreate, contains the domain name, description, and architecture slice as specified in §10.1 of architecture.md.
